# 自动化电商转型设计 — 全自动套利流水线

> 日期: 2026-08-23 · 状态: 已获用户批准（块 1/2/3 逐块确认）
> 所属项目: jp-us-arb-route（CN/JP 跨境代购决策引擎）

## 1. 背景与转型动机

现状是「分析环（Claude 推荐）+ 操作环（用户手动执行）」双环结构，8/17 锁定决策为撮合中介、
0 库存、「Claude 永不下单付款」。经过 brainstorming 对齐，转型方向确定为：

**全自动套利流水线** —— 系统自动比价 → 自动上架 → 自动下单 → 限额内自动付款 → 自动发货回填，
用户只处理异常。周人工介入 ≤30 分钟为验收标准。

## 2. 锁定需求（用户逐项确认）

| 维度 | 决策 |
|---|---|
| 自动化程度 | 全自动套利流水线（推翻「永不下单」红线） |
| 覆盖 leg | 🅳 电商带过去（CN→海外）+ 🅴 哥们仓（海外电商→哥们家→带回 CN）；🅲 出差代购排除（需现场）；🅰🅱 暂不进入执行环 |
| 销售端 | eBay（API）、Etsy（API）、闲鱼（RPA）、淘宝店（API） |
| 采购端 | 1688（API）、拼多多（RPA）、buyee（RPA）、amazon.co.jp/雅虎拍卖（RPA） |
| 资金模式 | 预收优先（买家付款到账后才触发采购） |
| 付款执行 | 限额内自动付：单笔 ≤¥300、日累计 ≤¥2,000（可配），超限转人工 |
| 验收标准 | 每周人工介入 ≤30 分钟 |
| 运行环境 | 本地 Mac 优先（家庭宽带 IP，封号风险低；API 类任务后续可迁 VPS） |
| 实现路线 | 演进式改造现有代码库（复用分析环 + 327 测试） |

## 3. 目标与非目标

**目标**
- 执行环接管操作环：上架/比价/下单/付款/发货回填全自动
- 所有异常收敛到 `awaiting_human` 状态 + 手机推送，用户只做裁决
- 复用现有资产：评分算法、SKU 池、额度账本、returns 记账、freshness、alerts、trips 行程表

**非目标（本期不做）**
- 🅰 撮合与 🅱 代购集运的自动化
- 自动定价训练（learned weights，v1.2 路线图保留）
- 多账号矩阵、员工协作
- 独立站（Shopify）与海外仓布局

## 4. 架构


## 5. 订单状态机

**🅳 电商带过去（CN → 海外）**
```
eBay/Etsy 自动上架 → 买家下单付款 → 【预收确认】→ 1688/拼多多比价下单
→ 限额内自动付 → 寄国内仓 → 【人工:出差带出境】→ 海外发货 → 完成
```

**🅴 哥们仓（海外电商 → CN）**
```
闲鱼/淘宝自动上架 → 买家付款 → 【预收确认】→ buyee/日亚雅虎下单
→ 限额内自动付 → 哥们家/转运仓 → 【人工:飞取带回】→ CN 发货 → 完成
```

规则：
- 每个状态有明确的自动出口和异常出口；异常统一转 `awaiting_human`
- 「飞带出境 / 飞取带回」两个物理环节复用现有 trips 行程表：订了机票后，
  流水线把积压订单聚合为「本次飞行带货清单」
- 上架文案由系统从 SKU 池模板自动生成（旧边界「用户写 listing」取消，
  模板可在 SPA 改）

**🅳 预收与囤货的取舍（明确化）**：预收优先模式下 🅳 不再预囤货，
改为「带已成交订单的货出境」；畅销品少量备货需人工在 SPA 批准，不走自动垫资。

## 6. 平台适配器

统一接口（Protocol）：

```python
class SellAdapter(Protocol):
    list_item(sku, title, price) -> external_id
    update_price(external_id, price)
    get_orders() -> list[Order]        # 含付款状态
    mark_shipped(external_id, tracking)
    delist(external_id)

class BuyAdapter(Protocol):
    search(sku, qty) -> list[Quote]    # 比价
    place_order(sku, qty, address) -> OrderRef
    pay(order_ref)                     # payguard 前置检查
    track(order_ref) -> ShipmentStatus
```

| 类型 | 平台 | 实现方式 |
|---|---|---|
| API | eBay（Trading API）、Etsy（Open API）、淘宝店（开放平台）、1688（开放平台） | HTTP 直连，令牌存 macOS Keychain |
| RPA | 闲鱼、拼多多、buyee、日亚/雅虎拍卖 | Playwright；登录态由用户首次手动登录后保存 `storage_state`，失效推送重登 |

RPA 风控节奏：同平台操作间隔 30–90 秒随机抖动，模拟人工节奏。

## 7. 支付守卫（payguard）

自动付款前四道检查，全部通过才允许扣款：
1. 买家付款已到账（预收优先）
2. 单笔 ≤¥300（可配）
3. 日累计 ≤¥2,000（可配）
4. 毛利为正：买家付款 − 采购成本 − 运费 > 0

任意不满足 → 订单转 `awaiting_human` + 推送确认，绝不自动扣款。阈值在 SPA 配置页可改。

## 8. 异常处理与人工干预

| 异常 | 系统动作 | 用户动作 |
|---|---|---|
| 验证码/登录态失效 | 停止该平台会话，推送 | 手机上重登一次 |
| 风控验证（短信/滑块） | 暂停该平台队列 | 手动通过后点「恢复」 |
| 采购价突变 >15% | 不下单，推送比价单 | 一键放行或取消 |
| 平台报错/超时 | 重试 3 次后退避 1 小时 | 一般不用管 |
| 退货/纠纷 | 转 `awaiting_human`，附退货规则建议 | 裁决 |

人工界面：现有 SPA 新增 **execution-section**（订单队列 + 待人工列表 + 一键放行/取消/改价）。

通知渠道：**默认微信 PushPlus**（国内手机免 VPN，送达最可靠；同类可换 Server酱）；
notify 接口做成 provider 抽象，预留 Telegram 实现，切换不动业务代码。

## 9. 安全与合规红线（硬规则，前置过滤）

- 禁售清单（威士忌/烟/肉/水果/种子/液体>100ml/中药>500g/象牙/假名牌等，
  见 `docs/daily/2026-08-17.md`「不能买」节）提升为 pipeline 前置过滤器，
  命中的 SKU 永不进入执行环
- 密钥与登录态存 macOS Keychain，不入 SQLite、不入 git
- 不存支付密码；自动付只在免密小额额度内发生
- RPA 单账号单会话；验证码一律停队列推人

## 11. 里程碑

| 阶段 | 内容 | 验证点 |
|---|---|---|
| **M0** | execution 包 + 状态机 + notify + dry-run | 全链路 dry-run 通过，零真实资金流动 |
| **M1** | 🅳 最小闭环（纯 API 无 RPA）：eBay 上架 + 1688 比价下单 | 真实预收一单跑通，付款限额内 |
| **M2** | 🅴 闭环：闲鱼 RPA + buyee RPA | 一单 RPA 真实下单成功 |
| **M3** | 扩平台：Etsy + 淘宝 API + 拼多多/日亚 RPA | 8 适配器全部可用 |
| **M4** | repricer 自动改价 + 行程联动带货清单 | 周人工 ≤30min，转型验收达成 |

M0 是第一个实现目标：纯工程增量、不碰真钱、风险为零。
